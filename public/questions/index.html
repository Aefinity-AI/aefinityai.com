The hard questions

Ten questions. What we found, and what is still open.

Each finding is from our own runs, at the scopes stated in the labs it links to.

  1. 01

    Question 1: Can two different computers produce the exact same AI output, bit for bit?

    What we found so far

    In our own runs, yes, for one narrow case: fp32 greedy decoding of one small model (SmolLM2-135M, 16 tokens), once the arithmetic is pinned in a written specification. The same digest came out on AVX2 and scalar x86 machines, an aarch64 phone and a free cloud CPU. Ten differently optimised x86_64 builds produced one identical dump. For training, default PyTorch gave different checkpoints on two CPUs even though the printed losses were identical, while a fixed-order C trainer gave identical checkpoints on five hosts including a phone, at toy scale (13,088 parameters).

    Still open

    Whether anyone outside our lab gets the same result; larger models; production precisions such as bf16; sampling, batching and quantisation. We have not tested those.

    Labs that address it

    • L01CIS-2: the same AI output, bit for bit, on different machines, Positive
    • L19E29: does the compiler's optimiser change the bits?, Positive
    • L12Training checkpoints across CPUs and instruction sets, Mixed
  2. 02

    Question 2: Does the same hold on graphics cards and under the usual speed shortcuts?

    What we found so far

    On one Tesla P100, an independent CUDA implementation matched the CPU digests, after two earlier GPU runs turned out to be false positives (the binary had really been built for the CPU) and were withdrawn. On a Tesla T4, one matrix multiply gave identical results with row-batched fp32 at batch sizes 1, 4 and 8, while grouped fp32 and int8 changed the result at every batch size, as predicted before the run.

    Still open

    Other GPU generations, tensor cores, whole-model batching beyond row-batched fp32, multi-GPU serving, and performance. The CUDA code is not public.

    Labs that address it

    • L02An NVIDIA GPU reproduces the CPU reference digest (Tesla P100), Positive
    • L03Batching and precision on a Tesla T4: which shortcuts change the digest, Positive
  3. 03

    Question 3: If someone changes a model's weights without telling you, how would you know?

    What we found so far

    Re-reading the output is a weak detector. In one run of 295 bit-flip trials, among the 247 where the output changed, a replay-style column missed 182 and a receipt-style check missed 82. An edited embedding row that no test prompt read was missed 40 of 40 times by text replay and by a top-5 check, while a check over the full computation caught all 40. A one-byte file corruption was stopped by a hash gate, but our own self-check would likely have repaired the file and hidden the corruption from a monitor. Also, 43 flips changed nothing in the computation, which a computation-level check by design does not flag.

    Still open

    Adversaries who optimise their tampering; other prompts, models and tensors; a scheduled, multi-host monitoring deployment.

    Labs that address it

    • L06One flipped bit in the weights: which checks notice?, Positive
    • L07Realistic edits to the embedding table, including one hidden row, Positive
    • L11Continuous validation: does a one-byte corruption get caught, and what hides it?, Mixed
  4. 04

    Question 4: Can you trust a record of what an AI agent did, and what does it cost?

    What we found so far

    A receipt that is replayed against pinned artifacts can catch edits an ordinary log display does not flag. Trying to break our own verifier found a hole: a genuine receipt filed under the wrong test item verified like a real one. Binding each receipt to its item closed that case. Receipts are not free: on one old laptop the episode with receipts took 2.51 times as long as a plain decode (the source calls that an upper bound), and verification took 40 seconds there and minutes on a weaker machine.

    Still open

    Whether the fix holds against tampering that was not hand-picked; cost on other hardware and at scale.

    Labs that address it

    • L08Receipt-verified agent evaluation, and the hole we found in our own verifier, Mixed
    • L09Ordinary logging versus replay-based receipts on one-field edits, Positive
    • L10What receipts cost on a real agent episode, Mixed
  5. 05

    Question 5: Can someone who has never seen our code rebuild the same bits from the written description alone?

    What we found so far

    Partly. A Rust version written from an internal memo did not match. A Rust version written from spec v0.1 matched all digests on its first CI run. A C version written from spec v0.2 matched three of four digests, and the mismatch led us to a defect in our own spec: the written order of the witness chain disagreed with the reference. We then found two more gaps by reading our spec critically: it names no Unicode version for letters, and it pins text to tokens but not tokens to text.

    Still open

    Independent humans doing the same; every one of these implementers was an AI coding agent run by one operator inside our organisation.

    Labs that address it

    • L04Clean-room reimplementations: one mismatch (from a memo), one match (from spec v0.1), one partial that exposed a spec error, Mixed
    • L14E24: the spec never says which Unicode version defines a letter, Mixed
    • L21E41: the spec pins how text becomes tokens, but not how tokens become text, Negative
  6. 06

    Question 6: How do we know our own tests test anything?

    What we found so far

    We broke our spec's rules one at a time: the official test noticed 12 of 16 breaks, and not the tie-break or the denormal-flush pin. Sampled accuracy checks gave comfortable wrong answers (at most 1 ULP) where exhaustive sweeps found much larger ULP errors near zeros of sin and cos. Exhaustive testing of exp found a real defect in a safety guard in our spec. A pre-registered 2 ULP bar was missed by our first fix and met by a second. We also retracted two wrong explanations of why the flush-to-zero rule never mattered.

    Still open

    Whether the test vector exercises every rule; the untriggered rules are protected only by separate self-tests.

    Labs that address it

    • L13E22: which spec rules does the test vector actually exercise?, Mixed
    • L16E26: sin/cos at very long contexts — the sampled answer was wrong, Mixed
    • L17E27: exp, ln and SiLU on every float32 input, and a defect in our spec, Mixed
    • L18E28, E36, E37: every internal activation compared against an independent implementation, Positive
    • L20E35 to E40: does the flush-to-zero rule ever matter? (after two wrong explanations), Null
    • L05Sin/cos accuracy for RoPE against a pre-registered 2 ULP bar (v0.2, v0.3, v0.3b), Mixed
    • L15E25: the RMSNorm multiply order matters, and our spec sentence saying otherwise was false, Positive
  7. 07

    Question 7: How can an outsider tell that a lab did not tune results after the fact, or quietly drop failures?

    What we found so far

    They cannot tell completely, and our own ledger page says so. We publish pass marks before runs, a hash-chained public ledger of the private register, numbered errata and a rule that mismatches count as results. The ledger cannot show when an experiment ran. As of 2026-10-12 nobody outside the lab has reproduced or broken our results, and the public Hall of Divergence says so plainly.

    Still open

    An outside audit of whether our practice always matched our statement.

    Labs that address it

    • L23Our test standard and the public experiment ledger, Mixed
    • L24Open challenge: the Hall of Divergence, Null
  8. 08

    Question 8: Do speed numbers survive scrutiny?

    What we found so far

    Ours did not, at first. Our benchmark laptop was clamped to about a fifth of its clock, so every earlier number from it was retracted. A compiler setting removed all vector instructions and the binary ran 217 to 258 times slower. A pre-registered comparison of a no-OS build against a minimal Linux was held back after a surprising first result; we found one contributing cause in our own build (soft-float), and the question remains open. A '16% slower' claim copied from a source comment did not reproduce. An early version of our software printed benchmark lines that were fixed strings.

    Still open

    A clean, controlled speed comparison across machines. We make no general speed claim; the speed figures on this site are single measurements on named machines.

    Labs that address it

    • L27Retraction: our benchmark laptop was running at about one fifth speed, Negative
    • L28A compiler setting silently deleted our vector instructions, Negative
    • L29What does an operating system cost? A pre-registered result we held back, Held back
    • L30The '16% slower' lookup-table kernel claim, retracted, Negative
    • L31Audit of our own removed code: benchmark lines that measured nothing, Negative
  9. 09

    Question 9: Do published tricks for shrinking AI models actually work?

    What we found so far

    Some, within narrow limits. On two real small models, a rotation recovered 92.3% and 92.5% of the 4-bit activation collapse, though perplexity stayed above the baseline. A shortcut that skips the rotation was refuted, a super-weight lever was null at 135M parameters, and one of our own earlier null results was retracted. Lossless coding of a ternary 2B model reached 1.532 bits per weight, about 4% below ideal packing. A stock soft-prompt recipe gave outputs wrong by about 300 times on one layer when we ran it.

    Still open

    Models above about 0.6B parameters, quantisation-aware training, and deployable int4 kernels.

    Labs that address it

    • L25RANGER mock run: low-bit quantization ideas tested on synthetic tensors, Mixed
    • L26RANGER Phase 1: the quantization ideas on real models (SmolLM2-135M, Qwen3-0.6B), Mixed
    • L32E-S1: how far can a ternary 2B model be compressed without loss?, Null
    • L33Claims from the literature that failed when we ran them, Negative
  10. 10

    Question 10: Can a tiny model be evaluated in a way anyone can repeat exactly, and what does it score?

    What we found so far

    The 160-item evaluation repeated exactly on one machine (20 of 20 self-consistency items). The model scored poorly, which was expected from a 135M base model with simple heuristics: 3 of 60 on truthfulness, 5 of 60 on a tool-use proxy and 10 of 20 on refusal probes, which the source says is chance. The point was repeatability, not accuracy.

    Still open

    Cross-host verification of the evaluation, and anything about larger or instruction-tuned models.

    Labs that address it

    • L22ev-1: a 160-item mini evaluation on the pinned 135M model, Mixed

Open questions we have not tested yet

No results here. These are questions our own limits sections point at. Nothing below has been measured.

  • Does bit-exact reproduction survive production serving?

    The spec covers fp32 greedy decoding on small open models, mostly CPU. bf16 and GPU serving, sampling, batching and larger models are outside it today. We have not tested them.

  • Do receipt checks hold against someone who optimises the tampering?

    Our tampering tests used hand-picked and harness-chosen edits. We have not tested an adversary who knows the verifier.

  • Will anyone outside our lab reproduce the results, or break them?

    Not yet known. No unaffiliated reproduction is recorded. The Hall of Divergence is the standing invitation.

  • Does reproducible output say anything about whether an answer is correct, safe or fair?

    We have not tested this. Reproducibility shows that two machines computed the same thing, not that the thing is good.

  • Which other rules in the spec does the test vector never exercise?

    We tested 16 single-rule mutations. We have not mapped the rest.
