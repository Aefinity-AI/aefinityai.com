L05 2026-08-29 Mixed Q6 · Do our tests test anything

Sin/cos accuracy for RoPE against a pre-registered 2 ULP bar (v0.2, v0.3, v0.3b)

QuestionIs the pinned sin/cos accurate enough for long contexts, measured against a bar we set before we tested?

Run by us; no unaffiliated reproduction

01Why it matters

Rotary position encoding feeds sin and cos with large angles at long context. If the pinned functions are inaccurate there, the spec pins a bad answer exactly.

02Method, step by step

  1. Write the pass mark down first: within 2 ULP of the correctly rounded f32 value.
  2. Build a 60-digit-precision reference (mpmath) for the angles up to position 8192 on two models.
  3. Score three versions: the original, a version with a higher-precision reduction only, and a version with octant reduction plus new polynomials.
  4. Report each against the bar.

Method as recorded

A pre-registration set a 2 ULP bar (oracle within 2 ULP of correctly-rounded f32) before the v0.3 fix was implemented. An mpmath 60-digit oracle covered RoPE angles for positions up to max_position_embeddings=8192, using the SmolLM2-135M (theta=1e5) and Qwen2.5-0.5B (theta=1e6) values. It compared three versions of the sin/cos reduction. The v0.3b mechanism was added by a coordinator directive after v0.3 missed the bar. Local x86_64 sandbox harness (scripts/h2m_accuracy_harness.py). Run by us.

03Results, exact and sourced

  1. R1The pre-registration was written before implementation.

  2. R2v0.2 (f32-only reduction, Taylor polynomial) had errors up to 115198 ULP for sin and up to 163969 ULP for cos, in the local oracle run.

  3. R3v0.3 (f64-staged reduction only) cut the error by roughly 55 to 70 times, with a max of 2813.5 raw ULP, and still missed the 2 ULP bar. The doc attributes the residual to the unchanged Taylor polynomial.

  4. R4v0.3b (octant reduction plus separate minimax polynomials) reached a maximum of 1.5 ULP for sin and cos on both models and met the bar, in the local harness run.

04What it does NOT show

Cross-ISA or CI confirmation (pending when written), positions above 8192, or that the final mechanism was pre-registered. It was added after the second version missed.

05Scope and caveats

  • Local x86_64 sandbox harness numbers only. CI runs were dispatched but were still in flight when the document was written, and the doc records no CI confirmation. Cross-ISA (aarch64) confirmation was pending.
  • Positions 0 to 8192 only. The v0.3b run used a dense grid (stride 7, plus positions 0 to 19 and the last position), not every position.
  • The 2 ULP bar was pre-registered for the v0.3 mechanism. The v0.3b mechanism was chosen after v0.3 missed, so it was not itself pre-registered.
  • The doc says the v0.3 ULP counts are inflated near sin/cos zero-crossings, a known property of the ULP metric. The v0.3 filtered figure (values with |sin/cos| >= 1e-2) is up to 486.5 ULP.
  • The work sits on branch cm/e15m-spec-v0.3-rope with 'Do NOT merge to main pending review'. The doc is on main, but the branch URL returns 404 unauthenticated, so the branch work is not public.
  • Gate (3), the token-match oracle runs, was not re-run for v0.3b in that pass.
  • Run by us; no unaffiliated reproduction.

06Outcome

Mixed

Some parts held, some did not, or we corrected ourselves.

07What we learned

Fixing only the reduction improved the error a lot and still failed the bar, because the polynomial was now the dominant error. We kept the bar and changed both the reduction and the polynomials, which met it in the local harness.
