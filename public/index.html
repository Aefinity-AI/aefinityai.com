AI inference you can check, not just trust.

We build CIS-2: an open specification and verifier for bit-exact fp32 transformer inference. The same pinned model and the same input produce the same bits on every conforming machine, and anyone can reproduce that claim on their own hardware in under fifteen minutes.

Reproduce it yourself CIS-2 on GitHubGitHub Conformance datasetDataset

What it is not: CIS-2 does not show that a model's answer is correct, safe or fair. It covers fp32 greedy decoding on small open models, mostly on CPU; production bf16/GPU serving is outside the spec today. 01How it works

Run it once. Replay it on another conforming machine.

A receipt binds an output to a pinned model, an input and a verifiable digest. A verifier on a machine separate from yours replays the run and compares every digest, so the claim rests on the record rather than on our word.

  1. Step 1

    Your machine

    Runs a pinned open model on an input and emits a CIS-2 receipt for that request.

  3. Step 2

    Receipt

    Binds the output to the pinned model, the input and a verifiable digest.

  5. Step 3

    Replay elsewhere

    A conforming machine running the open verifier replays the receipt: ours in a pilot, or yours, on your own hardware.

  7. Step 4 · compare every digest

    Match

    Same bits: for fp32 greedy decoding on the supported small open models, mostly on CPU, "this output came from this model on this input" checks out. It does not show the answer is correct, safe or fair.

    Mismatch

    Reported: every request whose digests differ and, where the per-step trace is available, the earliest step at which it diverges.

02What we build

A specification, the evidence, and receipts.

CIS-2 specification and verifier

One written spec. Two independent implementations. Identical digests.

A written specification of canonical floating-point semantics for fp32 transformer inference, with two clean-room implementations (C and Rust, written by isolated AI coding agents run by one operator) that produce identical digests from the specification text alone.

fp32C verifierRust referenceApache-2.0

Conformance evidence

Pinned test vectors, expected digests and machine fingerprints, published so a third party can re-run the checks and compare against the record rather than against our word.

Inference receipts and continuous validation

A receipt binds an output to a pinned model, an input and a verifiable digest. Continuous validation turns one-shot checks into an ongoing integrity monitor; in our one experiment the verifier's pinned artifact-hash check stopped a run on a weight file with one corrupted byte.

Context & prior work

Gensyn REEPrime Intellect TOPLOC

Verifiable inference and agent receipts are an active field with many good projects in it, for example Gensyn's REE and Prime Intellect's TOPLOC. We make no priority claim. CIS-2 is a written, open specification with independently implemented verifiers, so a third party can replay a run on its own hardware. The repository also holds a design note for a prototype receipt-gated tool gateway for agents (the prototype code is not in this repository); it was tested against hand-constructed attacks alone.

03Reproduce it yourself

Don't take our word. Run it.

No account, no token and no GPU are needed.

What the full self-check does

  1. 1Builds the Rust reference and the C verifier.
  2. 2Downloads the pinned weights from Hugging Face.
  3. 3Runs nine or ten checks against the repository's own pinned digests.
  4. 4Ends in a PASS or FAIL line against the pinned HuggingFaceTB/SmolLM2-135M test vector.

It needs

  • git
  • curl
  • gcc
  • make
  • objdump
  • a Rust toolchain

A shorter path checks the four pinned digests with the C verifier alone and needs no Rust toolchain.

selfcheck.shfull · C + Rust 
$ git clone https://github.com/Aefinity-AI/cis2-spec && cd cis2-spec && ./selfcheck.sh
# ends with a PASS or FAIL line

# ends with a PASS or FAIL line

05Limits, stated plainly

What we do not claim.

The main caveats on this page, in one place; the scoped details stay with each result.

  1. 01
    Not a correctness, safety or fairness check.CIS-2 does not show that a model's answer is correct, safe or fair. A matching receipt shows a computation was reproduced, not that the answer was right.
  2. 02
    Narrow scope today.fp32 greedy decoding on small open models, mostly on CPU. Production bf16/GPU serving is outside the spec today.
  3. 03
    No unaffiliated reproduction yet.No unaffiliated party has reproduced it yet; every run listed on this page was done by us.
  4. 04
    Some kernels do not match, by design.Grouped and int8 GPU kernels do not match the fp32 digests, and the record says so.
  5. 05
    Not everything is in the repository.The CUDA code behind the GPU runs is not in the repository. The receipt-gated tool gateway is a prototype described in a design note; its code is not in the repository, and it was tested against hand-constructed attacks alone.
  6. 06
    Written by AI agents, run by one operator.The two clean-room implementations (C and Rust) were written by isolated AI coding agents run by one operator.
  7. 07
    Continuous validation rests on one experiment.In our one experiment the verifier's pinned artifact-hash check stopped a run on a weight file with one corrupted byte.
  8. 08
    No priority claim.Verifiable inference and agent receipts are an active field with many good projects, for example Gensyn's REE and Prime Intellect's TOPLOC.
  9. 09
    No confirmed regulatory mapping.We think this is relevant to record-keeping and traceability requirements; no auditor or lawyer has confirmed that mapping. Not a certification, and not legal advice.
  10. 10
    Peer review in progress.A related research manuscript is under confidential peer review. Venue and submission details are not listed publicly.
  11. 11
    Each integrity demonstration is one small-scale test.Each result linked under Evidence is a single test, with its scope (model, prompts, hardware) given on its card and in the linked record.

06Why it matters

From trust in the operator to a check you can run.

The one claim CIS-2 makes checkable:

This output came from this model on this input.

For fp32 runs of the supported small models, bit-exact replay turns this one specific claim into something a customer or an auditor can check on their own machine.

Most claims about an AI system's behaviour rest on trust in the operator. For fp32 runs of the supported small models, bit-exact replay turns one specific claim, "this output came from this model on this input", into something a customer or an auditor can check on their own machine. We think this is relevant to record-keeping and traceability requirements; no auditor or lawyer has confirmed that mapping. A tolerance-based comparison cannot show that the exact computation was reproduced; whether you need that is the question a pilot answers.

We are careful about what this does not do. CIS-2 does not make a model correct, safe or fair. It makes the provenance of an output checkable, so that the harder questions can be asked about a fixed, agreed-upon artifact instead of a moving target. For how this fits into the broader AI safety landscape (evaluation reproducibility, monitoring, accountability, high-assurance deployment), see CIS-2 and AI Safety.

One-shot checks are useful; continuous validation is stronger. A completed continuous-validation experiment on ordinary older hardware is published as 2026-09-27 Continuous Validation.

07Work with us

Paid pilots: your pipeline, replayed elsewhere.

One of your inference pipelines emits CIS-2 receipts, our verifier replays them on a machine separate from yours, and you get a report of every mismatch plus a replayable artifact.

  1. 01

    Scoping

    One pipeline, one open-weight model, a set of requests, and what a match must mean for you.

  2. 02

    Receipts

    Your pipeline emits CIS-2 receipts for those requests, with the open (Apache-2.0) specification and verifiers; how much integration help you need is settled in scoping.

  3. 03

    Replay

    We replay the receipts on a machine separate from yours with the open verifier and compare every digest.

  4. 04

    Report

    A mismatch report, a replayable artifact your own staff can re-run, and a plain statement of limits.
